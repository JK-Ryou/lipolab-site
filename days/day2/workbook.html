PART 1

1. MCP — Agent와 도구를 잇는 표준 규격

MCP = 도구 명세 + 실행 코드 + 인증 정보 + 전송 방식. Agent가 외부 도구를 어떻게 쓸지 정하는 프로토콜입니다.

1-1. 일반 앱과 Agent 앱의 차이

노트: 기존 앱은 모델을 사용하지 않고, Agent 앱은 모델이 도구를 고른다.

구분동작 방식도구 사용
일반 Application개발자가 정해 놓은 로직대로만 실행없음 (코드로 직접 호출)
Agent Application모델이 판단하고 도구를 선택내부 직접 제작 또는 MCP로 외부 연결

IT 비유: 일반 앱이 "레시피 그대로 요리하는 조리 기계"라면, Agent 앱은 "재료를 보고 스스로 레시피를 정하는 셰프"입니다. 셰프가 어떤 도구(칼, 냄비 등)를 고를지 알려주는 규격이 MCP입니다.

AgentCore Gateway란

AWS의 원격 MCP 서버 관리 서비스입니다. Day 1 워크북에서 확인한 내용으로는, API·Lambda·기존 서비스를 MCP 호환 도구로 변환하고 기존 MCP 서버에 연결하는 역할을 합니다. "원격 MCP 서버를 만들어주는 것"이라는 노트 표현은 이 기능을 가리킵니다.

1-4. MCP 서버 구현 2단계

  1. 서버 파일 만들기 — Claude Code에 "FastMCP 써서 엑셀 파일을 MCP 서버로 만들어줘"처럼 요청합니다. FastMCP는 Python 기반의 MCP 서버 구축 라이브러리입니다.
  2. Claude Code에 등록 — "내가 만든 MCP 서버를 연결해줘"라고 요청합니다. 등록 후 Claude Code를 한 번 껐다 켜야 반영됩니다.

혼자 쓸 때 vs 팀과 쓸 때

  • 나만 쓴다면 stdio로 만들어도 됩니다. 로컬에서 실행되고 Claude Code와 표준 입출력으로 통신합니다.
  • 팀원과 함께 쓰려면 streamable HTTP 방식으로 만들어야 합니다. 이때 AgentCore Gateway를 써서 서버로 배포하면 팀 전체가 같은 도구를 씁니다.

2. DB & SQL — 데이터를 담고 꺼내는 구조

2-1. DB의 종류

종류특징언제 쓰나
엑셀파일 1개, 내 PC에만 존재, 동시 편집 불가간단한 개인 작업
RDB (관계형)테이블, 스키마, SQL로 관리. 가장 일반적일반 업무 데이터 (고객, 상품, 거래 등)
Graph DB노드와 관계(엣지)로 구성. 연결 관계 탐색에 강함Ontology 구축, 지식 그래프
Vector DB임베딩 벡터로 저장, 유사도 기반 검색RAG 구축 시 (FAQ, 문서 검색)
데이터레이크정형·반정형(.json)·비정형(이미지, 로그 등) 모두 수용대규모 데이터 통합 저장

오늘 실습의 고객·금융 데이터는 RDB(Aurora MySQL)였고, RAG를 쓰려면 Vector DB가 따로 필요합니다. AWS에서는 OpenSearch가 Vector DB 역할을 할 수 있습니다.

2-2. RDB 핵심 개념

데이터, 스키마, SQL

개념설명
데이터실제 저장된 값 (행과 열로 이루어진 테이블)
스키마데이터의 구조와 규칙 정의 — 데이터를 위한 메타데이터. 열 이름, 데이터 타입, 제약 조건 등 포함
SQL데이터의 CRUD를 위한 언어 (Structured Query Language)

PK(Primary Key)와 스키마 설계

  • PK는 각 행을 유일하게 식별하는 값입니다. 주민번호, 학번, 계좌번호처럼 중복이 없어야 합니다.
  • 테이블 간 관계는 Key(예: product_id)로 연결합니다. 이 Key를 통해 여러 테이블의 데이터를 묶어서 조회할 수 있습니다.
  • 스키마를 나중에 추가하면 이전 데이터에 null이 생깁니다. 데이터 일관성이 깨지고 분석이 복잡해지므로, 처음 설계가 매우 중요합니다.

스키마 변경이 어려운 이유 — 실무 의미

예를 들어 고객 테이블에 "신용등급" 열을 나중에 추가하면, 그 이전에 저장된 고객 데이터에는 모두 null이 들어갑니다. 이 null을 어떻게 채울지(기본값 설정, 일괄 업데이트 등)를 결정해야 하고, 이를 참조하는 다른 테이블이나 API가 있다면 그것도 함께 수정해야 합니다. 처음부터 "어떤 데이터가 필요할까"를 충분히 논의하는 게 나중의 공수를 줄입니다.

2-4. MCP를 활용한 자연어 질의

Claude Code에 MCP 서버를 연결하면 자연어로 DB를 조회할 수 있습니다. 모델이 MCP 도구를 고르고, 도구가 SQL을 실행해 결과를 돌려주는 구조입니다.

자연어 질의가 가능한 이유

  • 모델이 MCP 도구 명세(어떤 데이터를 어떻게 조회할 수 있는지)를 읽고 적절한 도구를 고릅니다.
  • 도구가 자연어 의도를 SQL 쿼리로 변환해 실행합니다.
  • 이전에는 개발자가 SQL을 직접 작성해야 했지만, 이제는 자연어로 지시하면 됩니다.

3. API — 시스템끼리 대화하는 창구

3-1. API 개념

API = 내부 구현을 숨기고 정해진 방식으로만 데이터를 주고받는 창구. 보안과 추상화가 핵심.

노트: "실제 동작 방식에 대한 이해 없이 API 호출 방식만 알면 원하는 데이터를 검색, 조회 가능" — 이것이 API의 추상화입니다.

추상화

API를 사용하는 쪽은 내부 로직을 몰라도 됩니다. 요청 형식과 응답 형식만 알면 됩니다.

보안과 통제

정해진 방식으로만 요청·응답을 허용해 DB를 직접 노출하지 않고 접근 방식을 통제합니다.

3-2. HTTP CRUD

동작HTTP 메서드SQL 대응특징
CreatePOSTINSERT요청 본문(body)에 데이터를 담아 전송
ReadGETSELECTURL 파라미터로 조건을 전달, 멱등성(여러 번 호출해도 같은 결과)

강의 중 질문: GET vs POST — MCP 연결에 POST를 쓴 이유는?

일반적으로 데이터 조회에 GET, 생성에 POST를 씁니다. 그런데 MCP 프로토콜은 도구 이름과 입력값을 JSON 본문(body)에 담아 전달하는 방식으로 설계되어 있어, 이때 POST를 씁니다. 이처럼 HTTP 메서드 선택은 "CRUD 의미"보다 프로토콜 설계 방식에 따라 달라질 수 있습니다. 오늘 실습에서 본 POST https://.../mcp는 MCP 연결 요청이었고, 데이터 생성이 아니었습니다.

3-3. 자연어 질의 흐름 — 3단계 변화

단계방식누가 SQL을 작성하나
1단계SQL 직접 조회개발자가 직접 작성
2단계API를 통해 조회개발자가 API 엔드포인트 설계, 내부에서 SQL 실행
3단계Agent를 통해 자연어 조회모델이 도구를 고르고, 도구가 SQL 실행

4. 실습 가이드 — 자연어 질의 흐름 재현하기

오늘 실습의 핵심은 "자연어 질문 → MCP → API → SQL → 결과 반환" 전 과정을 한 번에 확인하는 것이었습니다. 아래는 실습 타임라인과 각 단계에서 일어난 일입니다.

실습 환경

  • Aurora MySQL: SQL 콘솔 역할. 금융 고객·상품 데이터를 담고 있음
  • API Gateway: API 콘솔 역할. SQL 쿼리를 HTTP API로 래핑해 제공
  • AgentCore Gateway: MCP 콘솔 역할. Claude Code가 API를 MCP 도구로 사용할 수 있도록 연결

실습 · 자연어로 금융 고객 조회하기

AWS 의존: Aurora MySQL, API Gateway, AgentCore Gateway 실습 목표: 자연어 질의 전 과정 확인

자연어 프롬프트

학생 고객군 중 튼튼적금에 가입한 고객을 이름순으로 5명만 찾아줘

실습 타임라인 (강의 노트 기준)

  1. 질문 — 사용자가 자연어로 위 프롬프트를 입력합니다.
  2. 요청 — AgentCore Gateway로 MCP 연결 요청이 POST로 전송됩니다.
  3. 도구 선택 — 모델이 도구 명세를 읽고 어떤 API를 호출할지 결정합니다.
  4. API 호출 — 도구가 HTTPS 요청을 만들어 API Gateway로 전송합니다.
  5. SQL 실행 — API Gateway가 Aurora MySQL에 SQL 쿼리를 실행합니다.
  6. 결과 반환 — SQL 실행 결과가 API → MCP 도구 → Agent 순으로 전달됩니다.
  7. 최종 답변 — 모델이 결과 데이터를 자연어로 정리해 답합니다.

강의 중 질문 ① — "5명만"이라는 조건이 SQL에 없었던 이유

조회 결과에서 5명이 나왔지만 실제 SQL에는 LIMIT 5가 없었습니다. 모델이 "5명만"이라는 조건을 SQL 레이어가 아니라 응답 출력 단에서 처리했을 가능성이 있습니다. 이처럼 자연어 조건이 어느 레이어에서 실행되는지는 MCP 도구 명세와 모델의 해석 방식에 따라 달라집니다. 정확하게 SQL에 반영하려면 프롬프트에 "SQL에서 LIMIT을 써서"처럼 명시적으로 지시하거나, 도구 명세에 조건 처리 방식을 명확히 정의해야 합니다.

REVIEW

6. 복습 문제

동료와 함께 풀어 보세요. 질문을 누르면 답이 열립니다.

Q1. MCP의 구성요소 4가지를 말해 보세요.

도구 명세(모델이 읽는 사용 설명서), 실행 코드(MCP 서버 자체), 인증 정보(접근 제어), 전송 방식(로컬 stdio 또는 원격 streamable HTTP)입니다.

Q2. 혼자 쓰는 MCP 서버와 팀이 함께 쓰는 MCP 서버는 어떻게 다르게 구성하나요?

혼자 쓴다면 로컬(stdio)으로 만들어도 됩니다. 개인 PC에서 실행되고 Claude Code와 표준 입출력으로 통신합니다. 팀과 함께 쓰거나 서비스로 제공하려면 원격(streamable HTTP) 방식으로 만들어야 하며, AWS AgentCore Gateway를 써서 배포합니다.

Q3. PK(Primary Key)가 중요한 이유는 무엇인가요?

PK는 각 행을 유일하게 식별합니다. 테이블 간 관계를 연결하는 기준값이기도 합니다. 나중에 바꾸면 이를 참조하는 모든 테이블과 API를 함께 수정해야 하므로, 처음 설계 시 신중하게 정해야 합니다.

Q4. SQL CRUD 명령어와 HTTP CRUD 메서드를 각각 짝지어 보세요.

INSERT ↔ POST (생성), SELECT ↔ GET (조회), UPDATE ↔ PUT (수정), DELETE ↔ DELETE (삭제)입니다. 개념은 같고 표현이 다릅니다. API가 SQL 위에서 데이터 접근을 래핑해 제공하기 때문에 두 레이어가 나란히 존재합니다.

Q5. 자연어 질의의 3단계 흐름을 순서대로 설명해 보세요.

① 사용자가 자연어로 질문합니다. ② Agent(모델)가 도구 명세를 읽고 어떤 MCP 도구(API)를 쓸지 결정합니다. ③ 도구가 HTTPS 요청을 만들어 API 서버로 전송하고, 서버가 SQL을 실행합니다. ④ 결과가 도구 → Agent → 사용자 순으로 전달되고, 모델이 자연어로 정리해 답합니다.

Q6. "5명만 찾아줘"라고 했는데 SQL에 LIMIT이 없었습니다. 왜 그럴 수 있나요? 어떻게 하면 SQL에 반영할 수 있나요?

모델이 "5명만"이라는 조건을 SQL 레이어가 아닌 응답 출력 단에서 처리했을 가능성이 있습니다. SQL에 반영하려면 프롬프트에 "SQL에서 LIMIT 5를 써서"처럼 명시적으로 요청하거나, MCP 도구 명세에 개수 조건을 처리하는 파라미터를 명확히 정의해야 합니다.

Q7. 할루시네이션을 줄이기 위한 세 가지 방법은?

① 데이터의 질 관리: 최신성·정확성을 모니터링하고 변화를 추적합니다. ② 프롬프트 가이드: "모르면 모른다고 해"처럼 명확한 지시를 줍니다. ③ 결과 검증: GenAI는 확률 기반이므로 항상 결과를 확인합니다. 데이터 분포나 정책이 바뀌면 결과가 크게 달라질 수 있음을 인지합니다.

Q8. GET과 POST의 차이는? MCP 연결 요청에 POST를 쓰는 이유는?

일반적으로 GET은 데이터 조회(URL 파라미터로 전달), POST는 데이터 생성 또는 복잡한 요청(요청 본문에 JSON 데이터를 담아 전달)에 씁니다. MCP 프로토콜은 도구 이름과 입력값을 JSON 본문에 담아 전달하도록 설계되어 있어 POST를 씁니다. HTTP 메서드 선택은 CRUD 의미보다 프로토콜 설계 방식에 따라 달라질 수 있습니다.

Q9. FastMCP로 내 엑셀 데이터를 Claude Code에서 자연어로 쓰려면 어떻게 하나요?

① "FastMCP 써서 이 엑셀 파일을 MCP 서버로 만들어줘"라고 요청해 서버 파일을 만듭니다. ② "내가 만든 MCP 서버를 연결해줘"라고 요청해 Claude Code에 등록합니다. ③ Claude Code를 한 번 껐다 켜야 반영됩니다. 이후 자연어로 엑셀 데이터를 조회·분석할 수 있습니다. 혼자 쓴다면 stdio(로컬) 방식으로 충분합니다.
